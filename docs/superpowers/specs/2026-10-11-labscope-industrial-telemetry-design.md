# LabScope 工业设备遥测与实时监控平台设计

## 1. 目标与当前基础

把现有 `lab-telemetry-monitor` 从本机内存型 WebSocket 演示升级为一个可部署、可观测、可复现压测的工业设备遥测与告警应用。应用继续使用相邻目录中的 Drogon 1.9.13 源码作为 C++ Web 框架，不修改 Drogon 上游文件；应用本身作为独立项目维护。

当前原型已经具备 Drogon HTTP/WebSocket 服务、设备序号和指标校验、每设备 256 条内存记录、浏览器实时订阅、Python 负载模拟器和自动化集成测试。现有一次本机记录约为 1,992 条/秒；它是模拟负载结果，不等同于持久化后的吞吐，也不作为新版本的性能证明。升级后保留可复现基准，并为每个版本保存独立结果。

首版目标是**设备监控与告警**，不是设备控制系统。成功标准如下：

- MQTT 为主要设备上报入口，Modbus TCP 后续通过相同采集接口接入。
- Web 控制台提供设备状态、遥测趋势、告警处理和平台运行状态。
- 数据持久化，进程与 broker 重启后仍可查询已提交的设备、历史和告警记录。
- 参考环境中持续 10 分钟处理 1,000 条/秒；保存硬件、软件版本、运行参数、延迟分位数、错误计数和资源占用。
- 服务端只在事务提交后发布应用层持久化确认；未收到确认的设备消息会重发，重复消息不重复入库；正常负载下实时页面在 2 秒内呈现最新推送。
- Docker Compose 可以重现开发环境和单机部署，提供运行、备份、恢复和配置说明。

## 2. 项目边界与组件

继续在 `lab-telemetry-monitor` 中演进，避免复制出第二份同类应用。后端使用 C++20 和 Drogon，采用模块化单体部署，按业务边界组织以下组件：

1. **设备管理与认证**：站点、设备、设备状态、设备 MQTT 凭据及轮换。
2. **MQTT 采集适配器**：订阅遥测主题，校验设备和消息，实施有界缓冲及消费背压。
3. **遥测存储与查询**：批量事务写入 PostgreSQL，提供有时间范围和条数上限的历史 API。
4. **在线状态与规则告警**：按最后一次有效上报计算在线状态；执行阈值和持续时间规则，管理告警状态与确认记录。
5. **实时分发**：将最新状态按设备/站点广播到已认证 WebSocket 订阅者，采用合并与限频控制消息量。
6. **Web 控制台**：Vue 3、TypeScript、Vite 和 ECharts 构建设备总览、设备详情、告警中心和系统状态页。
7. **模拟器及压测工具**：设备模拟器可配置设备数、消息频率、持续时间、指标分布和异常行为；压测输出机器信息、吞吐、延迟分位数、资源和数据正确性摘要。

Docker Compose 运行 Drogon 应用、Vue 静态站点/反向代理、Mosquitto MQTT broker 和 PostgreSQL。各组件通过配置连接；开发环境可使用默认演示凭据，生产部署文档要求替换凭据、启用 TLS、配置 MQTT 用户 ACL、备份数据库并轮转日志。服务暴露健康检查、结构化日志和 Prometheus 格式指标。首版不依赖 Redis 或独立消息总线。

## 3. 遥测协议与可靠性

设备以 MQTT QoS 1 发布遥测消息，主题格式为：

```text
labscope/v1/sites/{site_id}/devices/{device_id}/telemetry
```

设备订阅对应的应用层确认主题：

```text
labscope/v1/sites/{site_id}/devices/{device_id}/acks
```

JSON 消息格式为：

```json
{
  "schema_version": 1,
  "seq": 12345,
  "timestamp_ms": 1791710400000,
  "metrics": {
    "temperature_c": 38.4,
    "vibration_mm_s": 2.1
  }
}
```

每条记录保存设备时间、服务端接收时间、站点、设备、序号和测点值。消息校验包括注册设备和站点、凭据、最大消息大小、JSON 类型、测点数量、有限数值、序号单调性和可配置的时间偏差范围。序号间断会计数并显示；重复或低于已接受水位的序号不会覆盖最新值或重复写入。无效消息进入受限的拒绝记录/计数路径，不能因永久格式错误无限重投。

MQTT 协议层 QoS 1 PUBACK 只表示 broker 到订阅客户端的传输确认，不代表数据库已提交。为保证设备到数据库的端到端交付，服务端在数据库事务提交后才向设备专属 ACK topic 发布包含 `schema_version`、`seq`、`status` 和确认时间的 QoS 1 应用层确认，ACK 不设置 retained。状态为 `persisted` 表示新记录已提交，`duplicate` 表示相同或较旧序号已处理，`rejected` 表示永久格式/身份错误；瞬时数据库错误不发应用层确认。设备必须保留未确认消息并以相同设备 ID、序号和载荷重发；收到 `persisted` 或 `duplicate` 后从待发队列移除，收到 `rejected` 后移入本地失败队列供排查。暂时无 ACK 时采用有上限的退避重试，超出配置的重试期限后移入失败队列并告警。MVP 模拟器使用 SQLite 持久化待发队列，以覆盖模拟器进程重启。

采集回调将消息投递到有界队列，独立工作线程按设备顺序批量校验状态并在 PostgreSQL 事务中写入。每设备首版只允许一条未确认消息在途，维持序号顺序；设备可以在本地持久化后续采样。事务提交后，服务端发送应用层确认；若服务在提交后、确认送达前崩溃，设备会重发，服务端识别重复并重新发送确认。队列接近上限时施加消费背压，不能无界增长；持久化错误、队列暂停、拒绝、序号缺口、重复和重试均有指标。MQTT 客户端版本在依赖锁定时确定；协议层 PUBACK 时序不作为数据库可靠性的依据。

连接状态按可配置的设备上报超时判定，并区分从未上报、在线、过期和禁用。告警规则支持测点阈值、持续时间、迟滞和冷却时间；告警事件记录触发、恢复、确认人、确认时间和备注。WebSocket 推送聚合周期内的最新值，不承诺逐采样点刷新。历史接口限制时间窗口、分页和返回上限。

PostgreSQL 使用按天分区的遥测原始表，并以设备和时间建立查询索引。默认保留最近 24 小时原始样本，聚合为 1 分钟 min/max/avg/count 后保留 30 天；保留策略可配置，分区清理和聚合过程对服务健康状态可见。设备、规则、告警和审计数据保留独立于遥测过期策略。

## 4. Web 界面、接口和安全

首版控制台包含：

- **总览页**：站点/产线设备总数、在线/过期数量、当前采集速率、活动告警和近期趋势。
- **设备页**：搜索、筛选和分页；单设备详情显示在线状态、最后上报、序号缺口、测点趋势和告警时间线。
- **告警中心**：按站点、设备、严重度和状态筛选；授权用户可确认告警并写处理备注。
- **系统状态页**：MQTT 连接和消费状态、有界队列深度、持久化延迟、失败/重试/重复计数及进程健康状态。

REST API 提供站点/设备管理、遥测历史、告警规则和事件、运行统计及健康信息；WebSocket 用于已授权用户订阅特定站点或设备的最新状态。所有历史查询都有时间范围和分页上限，实时客户端断开后释放订阅资源。

Web 用户密码使用经审核的安全散列算法存储；登录后使用服务端可撤销的不透明会话，浏览器凭据放在 HttpOnly、SameSite Cookie 中，生产环境设置 Secure 并对变更请求执行 CSRF 防护。角色至少包含管理员、操作员和只读观察者。设备凭据与 Web 用户凭据分离；Mosquitto ACL 将设备限制在自身主题。管理操作写入审计记录。生产部署通过 TLS 反向代理保护 HTTP/WebSocket 与 MQTT 传输；秘密不提交到仓库。默认演示账号只允许用于本机 Compose 环境。

## 5. 部署、验证和交付阶段

开发者可以在现有 Windows/CMake 环境继续构建 C++ 服务；Docker Compose 提供完整 broker、PostgreSQL 和 Web 运行环境。面向 Linux 单机部署提供容器配置、持久卷、健康检查、配置说明、备份与恢复步骤。首版为单节点部署，数据库或 broker 不可用时平台进入明确的降级状态；不宣称自动故障切换或高可用。

验证包含 C++ 单元测试、API/数据库集成测试、MQTT broker 集成测试、前端构建检查及端到端冒烟流程。故障场景覆盖重复/乱序/超时/非法消息、broker 断连重连、数据库短暂不可用、数据库提交后 ACK 丢失、设备端重发及模拟器进程重启、告警迟滞/冷却、权限越权、WebSocket 客户端断开和有界队列满载。性能基准持续 10 分钟发送 1,000 条/秒，并记录端到端延迟分位数、入库延迟、错误计数、CPU、内存和磁盘；新版本结果不能覆盖旧版本记录。

实施拆为三个可审查阶段：

1. **工业遥测主链路**：MQTT 接入、PostgreSQL 持久化/分区/保留、设备管理、模拟器与可复现压测、Compose 部署。
2. **操作闭环与 Web 控制台**：认证/角色、趋势与告警页面、规则配置、告警确认、审计和 Prometheus 指标。
3. **协议扩展与现场部署准备**：实现 Modbus TCP 轮询适配器，共用设备/测点模型；完善 TLS、备份恢复和部署演练文档。

## 6. 明确不在首版范围

- 向 PLC/设备写寄存器或发送控制命令。
- 安全联锁、硬实时控制或功能安全认证。
- 多节点高可用、跨站点容灾、Kubernetes 或复杂微服务拆分。
- 在没有现场设备验证前宣称真实产线兼容性或生产 SLA。

## 7. 设计自检

- 需求与边界明确区分现有内存型原型、拟实现的持久化平台和未来 Modbus 阶段。
- MQTT 协议层确认与数据库持久化确认明确区分；只有数据库事务提交后才发布应用层 ACK，设备端待确认消息可重发且按序处理。
- 原始数据保留与聚合周期有明确默认值，避免按 1,000 条/秒目标无限保留原始记录。
- 单机 Compose 的能力和非高可用边界明确；性能目标需要连同环境与原始结果一起交付。
- 首版目标覆盖 C++ 后端、Web UI、设备接入、持久化、告警、观测、安全基线与部署文档，范围可按三个阶段实施。
